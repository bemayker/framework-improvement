# Implementation Plan, TEST-09: Version endpoint reports the build commit

## Feature
> A client can ask the API which build it is talking to.
>
> Acceptance criteria
> 1. `GET /api/version` returns 200 with `{"version": "<string>", "commit": "<string>"}`.
> 2. `commit` comes from one declared source (an environment variable set at build time, default `"unknown"`), never a string typed into the router.
> 3. The response body is defined by a Pydantic schema in `backend/app/schemas/`.
> 4. Unit and integration tests cover the set and unset commit paths.
>
> Notes: Backend only. Registers a router in `backend/app/main.py`, which TEST-06, TEST-07 and FEAT-1 also touched; all three are complete. Depends on: TEST-01.

## Plan Overview
Extend the existing TEST-05 `GET /api/version` endpoint so its response carries a second field, `commit`. The value is read from the `BUILD_COMMIT` environment variable by the settings module (`backend/app/core/config.py`, default `"unknown"`), shortened to its first 12 characters by the version service, and returned through the existing `VersionResponse` Pydantic schema. The backend Docker image accepts `BUILD_COMMIT` as a build argument and exposes it as an environment variable, and docker-compose forwards it. Backend only: no frontend, no database, no new dependency, no change to `backend/app/main.py`.

## Frontend Plan
No frontend changes required.

## Backend Plan
- Endpoints: `GET /api/version` (existing, `backend/app/routers/version.py`): now returns `VersionResponse(version=get_app_version(), commit=get_build_commit())`. No literal commit string in the router.
- Settings (`backend/app/core/config.py`): add `DEFAULT_BUILD_COMMIT = "unknown"` and a `_read_build_commit()` helper that returns `os.environ.get("BUILD_COMMIT")` stripped, or `DEFAULT_BUILD_COMMIT` when unset or blank. Add the field `build_commit: str = field(default_factory=_read_build_commit)` to `Settings`, so it is read per call like `database_url` and `cors_origins` (`coding_standards.md` Section 5, the invariant: every environment-varying value in the settings module is read the same way, with a documented default).
- Service layer (`backend/app/services/version_service.py`): add `COMMIT_LENGTH = 12` and `get_build_commit() -> str`, which returns `get_settings().build_commit[:COMMIT_LENGTH]`. Values of 12 characters or fewer, including `"unknown"`, come back unchanged. Update the module docstring to name TEST-09.
- Schema (`backend/app/schemas/version.py`): add `commit: str` to `VersionResponse`; update the docstring to name TEST-09.
- Repository layer: none (no data access).
- Migrations: none.
- Build wiring: `backend/Dockerfile` adds `ARG BUILD_COMMIT=unknown` and `ENV BUILD_COMMIT=${BUILD_COMMIT}`; `docker-compose.yml` adds `args: BUILD_COMMIT: ${BUILD_COMMIT:-unknown}` under `services.backend.build`; `.env.example` documents an optional, commented-out `BUILD_COMMIT=` line.

## API Integration Plan
No external API integration.

## API Contract
- Method: GET
- URL: `/api/version`
- Request: no body, no query parameters.
- Response: 200, `application/json`, schema `VersionResponse`:

```json
{"version": "0.1.0", "commit": "0123456789ab"}
```

With `BUILD_COMMIT` unset or blank:

```json
{"version": "0.1.0", "commit": "unknown"}
```

`version` is unchanged from TEST-05 (installed distribution metadata, or `"unknown"`). `POST /api/version` still answers 405.

## Technology Selection
- `BUILD_COMMIT` lookup: chose the standard library `os.environ.get` inside the existing dataclass `Settings` over adding `pydantic-settings` or reading `git rev-parse` at runtime, because the settings module already reads every other variable this way and a running container has no `.git` directory.
- Truncation to 12 characters: chose a plain string slice over any helper or dependency; no alternative is needed.
- Build-time injection: chose the native Docker `ARG` plus `ENV` pair and the compose `build.args` key over a generated version file, because they are the platform's own mechanism for a build-time value and add no file.
- No net-new module, component or dependency is introduced; every change extends an existing file.

## Manual verification plan
This feature has no UI. Every criterion is verified over HTTP with `curl` against a backend started on the host, plus the test suites. Run every command from the repository root.

### Criterion 1: `GET /api/version` returns 200 with `version` and `commit` strings
Prerequisites: backend dependencies installed (`uv sync --directory backend`); no `BUILD_COMMIT` exported in the shell; port 8010 free. The endpoint needs no database.
1. Start the backend: `uv run --directory backend uvicorn app.main:create_app --factory --port 8010` → the log ends with `Uvicorn running on http://127.0.0.1:8010`.
2. In a second terminal run `curl -i http://localhost:8010/api/version` → the status line reads `HTTP/1.1 200 OK` and the body is `{"version":"<the version in backend/pyproject.toml>","commit":"unknown"}`.
3. Stop the backend with Ctrl+C.

### Criterion 2: `commit` comes from `BUILD_COMMIT`, default `"unknown"`, first 12 characters when longer
Prerequisites: as for Criterion 1.
1. Start the backend with a full sha: `BUILD_COMMIT=0123456789abcdef0123456789abcdef01234567 uv run --directory backend uvicorn app.main:create_app --factory --port 8010` → the server starts.
2. Run `curl -s http://localhost:8010/api/version` → `commit` is `0123456789ab` (exactly 12 characters).
3. Stop the backend, start it again with `BUILD_COMMIT=abc123 uv run --directory backend uvicorn app.main:create_app --factory --port 8010`, and repeat the curl → `commit` is `abc123`, unchanged.
4. Stop the backend, start it with `BUILD_COMMIT= uv run --directory backend uvicorn app.main:create_app --factory --port 8010` (empty value), and repeat the curl → `commit` is `unknown`.
5. Open `backend/app/routers/version.py` → no commit string literal appears; the value comes from `get_build_commit()`.
6. Build-time path: run `docker compose build --build-arg BUILD_COMMIT=fedcba9876543210fedcba9876543210fedcba98 backend`, then `docker compose up -d backend` and `curl -s http://localhost:8010/api/version` → `commit` is `fedcba987654`. Run `docker compose down` afterwards.

### Criterion 3: The response body is defined by a Pydantic schema in `backend/app/schemas/`
Prerequisites: backend running as in Criterion 1 step 1.
1. Run `curl -s http://localhost:8010/openapi.json` and look under `components.schemas.VersionResponse` → it lists `version` and `commit`, both of type `string`, both required.
2. Open `backend/app/schemas/version.py` → `VersionResponse` declares `version: str` and `commit: str`.

### Criterion 4: Unit and integration tests cover the set and unset commit paths
Prerequisites: backend dependencies installed. The tests in these files need no database.
1. Run `uv run --directory backend pytest -q tests/unit/test_version_service_unit.py tests/unit/test_config_unit.py tests/integration/test_version_integration.py` → the run passes: its summary line reports no failed or errored test and the command exits 0.
2. Confirm the output (add `-v`) includes `test_get_version_returns_truncated_commit_when_build_commit_is_set` and `test_get_version_returns_unknown_commit_when_build_commit_is_unset`, both PASSED.
