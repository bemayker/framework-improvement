# Implementation Plan, TEST-07: Uptime endpoint

## Feature
> A small backend feature for the autonomous `/deliver` run (Arm E of measured run 2). Independent of TEST-08, which is frontend-only, so the two can be built in parallel.
>
> **What**
>
> `GET /api/uptime` reports how long the process has been running, so an operator can tell a restart from a long-lived process without reading container logs.
>
> **Acceptance criteria**
>
> 1. `GET /api/uptime` returns **200** with `{"uptime_seconds": <number>, "started_at": "<ISO 8601 UTC>"}`.
> 2. `uptime_seconds` is a non-negative number and increases between two calls a second apart.
> 3. `started_at` is captured once at application startup, not recomputed per request, and is serialised in UTC with an explicit offset.
> 4. The response body is defined by a Pydantic schema in `backend/app/schemas/`.
>
> **Notes**
>
> Router under `backend/app/routers/`, registered in `backend/app/main.py`, with unit and integration tests. Touches `main.py`'s router registration, so it must not run concurrently with another backend item that does the same.
>

## Acceptance Criteria
- [ ] `GET /api/uptime` returns 200 with a JSON body holding exactly two keys, `uptime_seconds` (a JSON number) and `started_at` (an ISO 8601 string in UTC).
- [ ] `uptime_seconds` is never negative, and a second call made one second after the first returns a strictly larger value.
- [ ] `started_at` is captured once when the process starts (a module constant evaluated when `app.main` imports the router), is identical on every response of one process, and is serialised in UTC with the explicit offset `+00:00` (for example `2026-09-14T09:51:03.412876+00:00`), never `Z` and never a naive timestamp.
- [ ] The response body is defined by the Pydantic model `UptimeResponse` in `backend/app/schemas/uptime.py`, the router returns that model rather than a bare dict, and `/openapi.json` references it as the 200 schema of `GET /api/uptime`.

## Plan Overview
Backend-only feature. Add `GET /api/uptime` to the FastAPI app as one router (`backend/app/routers/uptime.py`) and one response schema (`backend/app/schemas/uptime.py`), registered in `create_app()` in `backend/app/main.py` exactly as the version, health, echo and (by the time this builds) server-time routers are. The router module captures two constants once, when `app.main` imports it at process start: `STARTED_AT`, an aware UTC `datetime`, and `STARTED_AT_MONOTONIC`, the `time.monotonic()` reading taken beside it. The handler computes `uptime_seconds = time.monotonic() - STARTED_AT_MONOTONIC` and returns `UptimeResponse(uptime_seconds=..., started_at=STARTED_AT)`. The schema constrains `uptime_seconds` with `Field(ge=0)`, types `started_at` as `AwareDatetime`, and serialises it with a `field_serializer` that returns `value.astimezone(timezone.utc).isoformat()`, so the offset is written `+00:00` (criterion 3). No frontend work, no service or repository module, no migration, no new dependency.

Deliberate deviation from `coding_standards.md` Section 2.2, recorded here so the reviewer reads it as planned: no `backend/app/services/uptime_service.py` is created. Section 2.2's Router → Service → Repository pattern is for business logic and transactional boundaries; subtracting two clock readings and handing two module constants to a response model is neither, and CLAUDE.md's architecture note is "Keep every feature as small as possible". The merged precedent on this main is consistent with it: TEST-06's echo router and FEAT-1's server-time router (the concurrent item in this run, whose tracker feedback explicitly removed its service module) both construct a dependency-free response in the router, and the project keeps a service only where there is logic to hold (`version_service` resolves package metadata with a fallback, `health_service` runs a database probe). The run-2 build of this same item had a service module; matching the precedent that has merged since matters more than repeating that shape. The router still carries no business logic in the Section 2.2 sense.

Recorded assumptions (unattended-surface rule, `user_story_alignment.md` Section 4):
- "Application startup" is read as process start: `STARTED_AT` is evaluated when `app.routers.uptime` is imported, which happens when uvicorn imports `app.main`. The alternative, setting it on `app.state` inside `lifespan`, would widen this item's edit of `main.py` (the file it shares with FEAT-1) and make the handler depend on a `Request`; it was not chosen. In the test process the constant is captured when the test session imports `app.main`, so `uptime_seconds` there measures the test session, which is the correct reading of "the process".
- "Explicit offset" means `+00:00`, not the `Z` designator pydantic writes by default. This matches FEAT-1's `now` field, so the project's two timestamp endpoints serialise the same way.
- `uptime_seconds` is a float with fractional seconds (`total_seconds()`-style precision from `time.monotonic()`), not rounded and not an integer. The criterion says "a non-negative number" and asks for nothing finer.
- The response carries exactly the two keys the criterion names. No process id, hostname, version or human-readable duration is added.
- Elapsed time is measured on the monotonic clock rather than as `now - STARTED_AT`, so a wall-clock step backwards (an NTP correction) cannot produce a negative value or a decrease between two calls. `started_at + uptime_seconds` may therefore differ from the wall clock by the size of any such correction; that is intended and is not asserted tighter than a five-second sanity bound in tests.

## API Contract
- Method: GET
- URL: `/api/uptime`
- Request: no parameters, no body.
- Response 200 (`content-type: application/json`):

  ```json
  {"uptime_seconds": 83.417205, "started_at": "2026-09-14T09:51:03.412876+00:00"}
  ```

  `uptime_seconds`: JSON number, `>= 0`, fractional seconds, strictly increasing across successive calls of one process. `started_at`: ISO 8601 string, UTC, offset written `+00:00`, identical on every response of one process, microsecond precision as `datetime.isoformat()` writes it (a start captured on an exact second has no fractional part, which is still valid ISO 8601). Defined by `UptimeResponse` in `backend/app/schemas/uptime.py`; `/openapi.json` references `#/components/schemas/UptimeResponse` as the 200 schema of `GET /api/uptime`, with properties `uptime_seconds` (`type: number`, `minimum: 0`) and `started_at` (`type: string`, `format: date-time`), both required.
- No 4xx path of the application's own: the endpoint takes no input, so there is nothing to validate.
- Any other method on the path: 405 (FastAPI default, as with `/api/version`, `/api/health` and `/api/echo`).

## Technology Selection
- Elapsed-time measurement (criterion 2): chose the standard library's `time.monotonic()`, read once at import beside `STARTED_AT` and again per request, over `datetime.now(timezone.utc) - STARTED_AT`, because a monotonic clock cannot step backwards on a wall-clock correction, so "non-negative" and "increases between two calls" hold by construction and the schema's `ge=0` bound never has to reject a live response; and over a hand-written `max(0.0, ...)` clamp, which would hide the same correction rather than be immune to it.
- Startup capture (criterion 3): chose module-level constants in `routers/uptime.py`, evaluated when `app.main` imports the module at process start, over `app.state.started_at` set inside `main.py`'s `lifespan`, because import time is process start under uvicorn, it keeps this item's edit of the shared `main.py` to two lines, and the handler stays a plain function a unit test can call without a `Request`. No stdlib or platform feature records a process start time for a FastAPI app on its own.
- Response schema (criterion 4): chose a pydantic `BaseModel` (`UptimeResponse`; pydantic 2.13.4 ships with the installed FastAPI and matches every file in `app/schemas/`) with `Field(ge=0)` and pydantic's `AwareDatetime` type over a bare dict return (forbidden by criterion 4), over a `TypedDict` (FastAPI would not validate or document it as a component), and over hand-written validators for the non-negative and timezone-aware constraints, which the installed library expresses declaratively and publishes in the OpenAPI schema.
- UTC offset serialisation (criterion 3): chose a pydantic `field_serializer` returning `value.astimezone(timezone.utc).isoformat()` over pydantic's default datetime JSON encoding, because the default writes UTC as `Z` and the criterion asks for an explicit offset; `astimezone(timezone.utc)` (stdlib) makes the UTC half hold for any aware input rather than relying on the caller. It matches FEAT-1's `+00:00` pin so the project's two timestamp endpoints agree.
- Service module: chose to construct the response in the router over a net-new `services/uptime_service.py` (which the run-2 build had), because there is no business logic, transaction or external call for a service to own, and the merged TEST-06 precedent plus the concurrent FEAT-1 plan both settled this shape. Recorded as a Section 2.2 deviation in the Plan Overview.
- No net-new dependency is added by this feature, so no lockfile changes.

## Manual verification plan
None of the four criteria is verifiable through the application's own UI: no frontend consumes `GET /api/uptime`. The observable check is the HTTP response itself, read with `curl`, plus FastAPI's generated Swagger UI at `/docs` for criterion 4, which a person can read in a browser.

Prerequisites (shared by every block): Docker running; the stack up via `docker compose up -d --build` run from the repository root; `docker compose ps` shows the `backend` service running (the `db` service is not needed by this endpoint but the compose file starts it anyway); a terminal with `curl`; the backend is published on the host at `http://localhost:8010` (from `docker-compose.yml`).

### Criterion 1: `GET /api/uptime` returns 200 with `{"uptime_seconds": <number>, "started_at": "<ISO 8601 UTC>"}`
Prerequisites: the shared prerequisites above.
1. In a terminal, run `curl -i http://localhost:8010/api/uptime` → the first response line reads `HTTP/1.1 200 OK` and the headers include `content-type: application/json`.
2. Read the response body → a JSON object with exactly two keys, in the shape `{"uptime_seconds":83.417205,"started_at":"2026-09-14T09:51:03.412876+00:00"}`: `uptime_seconds` is a bare number (no quotes) and `started_at` is a quoted ISO 8601 timestamp with a `T` separator and a `+00:00` suffix. No other key is present.

### Criterion 2: `uptime_seconds` is non-negative and increases between two calls a second apart
Prerequisites: the shared prerequisites above.
1. Run `curl -s http://localhost:8010/api/uptime` → note the `uptime_seconds` value (for example `83.417205`); it is zero or greater, never a negative number.
2. Wait at least one second (`sleep 1` in the same terminal, then repeat the command) and run `curl -s http://localhost:8010/api/uptime` again → the new `uptime_seconds` is strictly larger than the value noted in step 1, by at least one second (for example `84.9`), and is still non-negative.
3. Run `docker compose restart backend`, wait until `docker compose ps` shows `backend` running again, then run `curl -s http://localhost:8010/api/uptime` → `uptime_seconds` is small (a few seconds at most), smaller than the value in step 2: the counter restarted with the process, which is the distinction the feature exists to make.

### Criterion 3: `started_at` is captured once at startup, not recomputed per request, and serialised in UTC with an explicit offset
Prerequisites: the shared prerequisites above.
1. Run `curl -s http://localhost:8010/api/uptime` → note the `started_at` string, for example `2026-09-14T09:51:03.412876+00:00`. It ends with `+00:00` (not `Z`, and not a bare timestamp with no offset).
2. Wait a few seconds and run `curl -s http://localhost:8010/api/uptime` again → `started_at` is byte-for-byte identical to step 1 while `uptime_seconds` has grown: the timestamp was captured once and is not recomputed per request.
3. Run `date -u` in the terminal → the current UTC time is later than `started_at` by roughly the `uptime_seconds` of step 2 (within a few seconds), which shows the value is in UTC rather than in the host's local zone.
4. Run `docker compose restart backend`, wait until `docker compose ps` shows `backend` running again, then run `curl -s http://localhost:8010/api/uptime` → `started_at` is now a later timestamp than in step 1 (the process restarted), still ending `+00:00`.
5. Open `backend/app/routers/uptime.py` in an editor → `STARTED_AT` is assigned once at module level with `datetime.now(timezone.utc)`, and the handler body reads it without reassigning it. This is the "captured once at startup" half, observable in source as well as in steps 2 and 4.

### Criterion 4: the response body is defined by a Pydantic schema in `backend/app/schemas/`
Prerequisites: the shared prerequisites above; a browser.
1. Open `http://localhost:8010/docs` in the browser → the Swagger UI lists a `GET /api/uptime` operation under the `uptime` tag.
2. Expand `GET /api/uptime` and read its `200` response → the example body has the keys `uptime_seconds` (number) and `started_at` (string, date-time) and the schema link names `UptimeResponse`.
3. Scroll to the `Schemas` section at the bottom of the page → `UptimeResponse` is listed with two required properties: `uptime_seconds` of type `number` with minimum `0`, and `started_at` of type `string` with format `date-time`.
4. Alternatively, in a terminal run `curl -s http://localhost:8010/openapi.json` → under `paths`, `/api/uptime`, `get`, `responses`, `200`, `content`, `application/json`, `schema`, the reference is `#/components/schemas/UptimeResponse`, and under `components`, `schemas`, `UptimeResponse`, `properties` has exactly the two keys `uptime_seconds` and `started_at`.
5. Open `backend/app/schemas/uptime.py` in an editor → it defines `class UptimeResponse(BaseModel)` with the fields `uptime_seconds: float = Field(ge=0)` and `started_at: AwareDatetime`, and `backend/app/routers/uptime.py` returns an instance of it, not a dict.
