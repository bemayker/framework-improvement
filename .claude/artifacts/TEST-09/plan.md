## Plan Overview

**`backend/app/main.py` is NOT touched by TEST-09.** The version router is registered there since TEST-05 and nothing about the registration changes. `backend/tests/unit/test_main_unit.py` is not touched either. BUG-01, planned in parallel and registering a `server_time` router in `main.py`, therefore has no file overlap with this item on `main.py`.

### Key decisions and assumptions
- One declared source: `Settings.build_commit` in `backend/app/core/config.py`, read from the `BUILD_COMMIT` environment variable per call through a `default_factory` (the same shape `database_url` and `cors_origins` use, so the settings module stays consistent with `coding_standards.md`'s rule that every environment-varying value in one settings module is read the same way, with a documented default). The default literal `"unknown"` lives only there, as the constant `UNKNOWN_BUILD_COMMIT`.
- Assumption (scope): a blank or whitespace-only `BUILD_COMMIT` is treated as unset and yields `"unknown"`, matching how `CORS_ORIGINS` treats a blank value. Surrounding whitespace is stripped before truncation. Reason: `docker-compose.yml` passes `${BUILD_COMMIT:-}`, which is an empty string whenever the host does not set it, and an empty `commit` would tell a client nothing.
- Truncation to 12 characters happens in the service, not in settings: settings hold the declared value as given, the service owns the presentation rule from the tracker comment.
- The service reads `get_settings()` per call (no module-level capture), so a test that sets `BUILD_COMMIT` with `monkeypatch` is seen by the session-scoped `client` fixture.
- "Set at build time" is satisfied by the deploy or CI process exporting `BUILD_COMMIT` before `docker compose up --build`; compose interpolates it into the backend container's environment. No Dockerfile `ARG` is added: the compose environment line is the one route, and a second route through the image would be a second source for the same value.
- `docker-compose.yml` uses `${BUILD_COMMIT:-}` and not `${BUILD_COMMIT:-unknown}`, so the default `"unknown"` has exactly one source (config.py) and never two.

## Backend Plan

- Core settings (`backend/app/core/config.py`): add module constant `UNKNOWN_BUILD_COMMIT = "unknown"`, a private reader `_read_build_commit() -> str` returning `os.environ.get("BUILD_COMMIT", "").strip() or UNKNOWN_BUILD_COMMIT`, and the frozen-dataclass field `build_commit: str = field(default_factory=_read_build_commit)` with a one-line comment naming the variable and its default. Update the module docstring to name TEST-09.
- Service layer (`backend/app/services/version_service.py`): add constant `COMMIT_DISPLAY_LENGTH = 12` and `get_build_commit() -> str` returning `get_settings().build_commit[:COMMIT_DISPLAY_LENGTH]`, with a docstring saying why (CI passes a full 40-character sha; clients get the short form). `get_app_version()` is unchanged. Module docstring names TEST-09.
- Schema (`backend/app/schemas/version.py`): `VersionResponse` gains `commit: str`. Both fields required.
- Router (`backend/app/routers/version.py`): `return VersionResponse(version=get_app_version(), commit=get_build_commit())`. No literal in the router.
- Repository layer: none (no data access).
- Migrations: none.

## API Contract
- Method: GET
- URL: `/api/version`
- Request: no body, no query parameters.
- Response 200, `application/json`, schema `VersionResponse`:

```json
{"version": "0.1.0", "commit": "0123456789ab"}
```

With `BUILD_COMMIT` unset or blank:

```json
{"version": "0.1.0", "commit": "unknown"}
```

- `version`: unchanged from TEST-05 (installed package metadata, `"unknown"` when the distribution is not installed).
- `commit`: `BUILD_COMMIT` stripped, at most its first 12 characters; `"unknown"` when unset or blank.
- `POST /api/version`: 405, unchanged.

## Technology Selection
- `BUILD_COMMIT` reading: chose the standard library `os.environ.get` inside the existing frozen `Settings` dataclass over adding `pydantic-settings` (not installed) or a new config module, because the project's settings module already reads every environment value this way.
- Commit truncation: chose a plain string slice over any helper or dependency; no stdlib call is narrower than a slice.
- `commit` response field: chose a field on the existing Pydantic `VersionResponse` (Pydantic is installed with FastAPI) over a new schema class, because criterion 3 is met by the existing schema module.
- No new dependency, no new module and no new file of application code: the item extends four existing files.

## Manual verification plan
This feature has no UI: every criterion is verified against the HTTP endpoint with `curl` and against the test suite. The backend listens on `http://localhost:8010` under `docker compose`.

### Criterion 1: `GET /api/version` returns 200 with `{"version": "<string>", "commit": "<string>"}`
Prerequisites: Docker running; repository root as the working directory; no `BUILD_COMMIT` exported in the shell.
1. Run `docker compose up -d --build backend db` → both containers report as started.
2. Run `curl -i http://localhost:8010/api/version` → status line `HTTP/1.1 200 OK`, header `content-type: application/json`, body `{"version":"0.1.0","commit":"unknown"}`.

### Criterion 2: `commit` comes from one declared source (`BUILD_COMMIT`, default `"unknown"`)
Prerequisites: as Criterion 1.
1. Run `BUILD_COMMIT=0123456789abcdef0123456789abcdef01234567 docker compose up -d --build backend` → the backend container is recreated.
2. Run `curl -s http://localhost:8010/api/version` → body `{"version":"0.1.0","commit":"0123456789ab"}` (the first 12 characters of the 40-character sha).
3. Run `BUILD_COMMIT=abc1234 docker compose up -d backend`, then `curl -s http://localhost:8010/api/version` → body `{"version":"0.1.0","commit":"abc1234"}` (7 characters, unchanged).
4. Run `BUILD_COMMIT= docker compose up -d backend`, then `curl -s http://localhost:8010/api/version` → body `{"version":"0.1.0","commit":"unknown"}`.
5. Open `backend/app/routers/version.py` → it contains no string literal for the commit; it calls `get_build_commit()`. Open `backend/app/core/config.py` → `"unknown"` appears once, as `UNKNOWN_BUILD_COMMIT`.

### Criterion 3: The response body is defined by a Pydantic schema in `backend/app/schemas/`
Prerequisites: backend running as in Criterion 1.
1. Open `http://localhost:8010/docs` in a browser and expand `GET /api/version` → the 200 response shows schema `VersionResponse` with `version` (string) and `commit` (string), both required.
2. Open `backend/app/schemas/version.py` → `class VersionResponse(BaseModel)` declares `version: str` and `commit: str`.

### Criterion 4: Unit and integration tests cover the set and unset commit paths
Prerequisites: uv installed; repository root as the working directory.
1. Run `uv run --directory backend pytest -q tests/unit/test_config_unit.py tests/unit/test_version_service_unit.py tests/integration/test_version_integration.py` → the summary line reports no failed or errored test and the command exits 0.
2. Read the test names in the output with `-v` added → `test_get_version_returns_commit_from_build_commit_env` and `test_get_version_returns_unknown_commit_when_build_commit_unset` are present and pass.
