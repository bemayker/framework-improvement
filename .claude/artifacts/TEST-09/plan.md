# Implementation Plan, TEST-09: Version endpoint reports the build commit

## Feature
> A client can ask the API which build it is talking to.
>
> Acceptance criteria
> 1. `GET /api/version` returns 200 with `{"version": "<string>", "commit": "<string>"}`.
> 2. `commit` comes from one declared source (an environment variable set at build time, default `"unknown"`), never a string typed into the router.
> 3. The response body is defined by a Pydantic schema in `backend/app/schemas/`.
> 4. Unit and integration tests cover the set and unset commit paths.
>
> Notes: Backend only. Registers a router in `backend/app/main.py`, which TEST-06, TEST-07 and FEAT-1 also touched; all three are complete. Depends on: TEST-01.

## Plan Overview
Backend only. Extend the existing TEST-05 version slice so `GET /api/version` also reports the build commit: a `build_commit` setting read from the `BUILD_COMMIT` environment variable (default `"unknown"`), a service function that normalizes and truncates it to 12 characters, a `commit` field on the existing `VersionResponse` Pydantic schema, and the router passing it through. Build-time wiring is a Dockerfile `ARG`/`ENV` pair and a compose build arg; `.env.example` documents the key. No frontend, no database, no new dependency, no new route.

## Frontend Plan
No frontend changes required.

## Backend Plan
- Endpoints: `GET /api/version` (existing, `backend/app/routers/version.py`): now returns `VersionResponse(version=get_app_version(), commit=get_build_commit())`. The router contains no commit literal.
- Settings (`backend/app/core/config.py`): add `build_commit: str` to the frozen `Settings` dataclass with a `default_factory` that reads `BUILD_COMMIT` per call, strips it, and returns `DEFAULT_BUILD_COMMIT = "unknown"` when unset or blank. Per-call reading matches the existing `database_url` and `cors_origins` fields and is what lets tests `monkeypatch` the variable against the session-scoped `client`.
- Service layer (`backend/app/services/version_service.py`): add `COMMIT_LENGTH = 12` and `get_build_commit() -> str`, which reads `get_settings().build_commit` on every call and returns `value[:COMMIT_LENGTH]`. The sentinel `"unknown"` (7 characters) passes through unchanged. Module docstring gains one line naming TEST-09 and the 12-character rule's source (the tracker clarification).
- Schema (`backend/app/schemas/version.py`): add `commit: str` to `VersionResponse`, docstring updated.
- Build wiring: `backend/Dockerfile` adds `ARG BUILD_COMMIT` and `ENV BUILD_COMMIT=${BUILD_COMMIT}` (no default in the Dockerfile; an empty value resolves to `"unknown"` in settings). `docker-compose.yml` adds `args: BUILD_COMMIT: ${BUILD_COMMIT:-}` under `backend.build`. `.env.example` gains a commented `BUILD_COMMIT=` entry explaining it is optional, set at build time, and truncated to 12 characters in the response.
- Repository layer: none (no data access).
- Migrations: none.

## API Integration Plan
No external API integration.

## API Contract
- Method: GET
- URL: `/api/version`
- Request: no body, no query parameters.
- Response: 200, `application/json`, body defined by `VersionResponse` in `backend/app/schemas/version.py`:

```json
{"version": "0.1.0", "commit": "8df9812ed349"}
```

  With `BUILD_COMMIT` unset or blank: `{"version": "0.1.0", "commit": "unknown"}`. With `BUILD_COMMIT=abc1234`: `"commit": "abc1234"`. With a 40-character sha: its first 12 characters. `version` keeps TEST-05's behaviour (package metadata, `"unknown"` fallback).
- Other methods: `POST /api/version` stays 405 (unchanged).

## Technology Selection
- Reading `BUILD_COMMIT`: chose the standard library `os.environ.get` inside the existing `Settings` dataclass over adding `pydantic-settings` (not installed) or a new config module, because the project's settings module already reads every environment value this way.
- Truncation to 12 characters: chose a stdlib string slice over `subprocess`/`git rev-parse --short` or any git library, because the value arrives from the environment and the container has no repository to ask.
- Build-time injection: chose the native Docker `ARG`/`ENV` pair and Compose `build.args` over a generated version file or an entrypoint script, because the platform covers it in two lines.
- No net-new dependency, component or module: every change extends an existing file.

## Manual verification plan
This feature has no UI: every check below is read from the API response, the OpenAPI document or the test run.

### Criterion 1: GET /api/version returns 200 with version and commit
Prerequisites: repository at the feature branch, `.env` copied from `.env.example`, Docker running; the backend needs no database for this endpoint.
1. From the repository root, run `BUILD_COMMIT=8df9812ed349fa26e4e14c316bc61757340b04ef docker compose up -d --build backend` → the backend container starts and listens on port 8010.
2. Run `curl -i http://localhost:8010/api/version` → the status line reads `HTTP/1.1 200 OK` and the body is a JSON object with exactly two keys, `version` (for example `"0.1.0"`) and `commit`, both strings.

### Criterion 2: commit comes from BUILD_COMMIT, default "unknown", truncated to 12
Prerequisites: the stack from Criterion 1.
1. With the container built in Criterion 1 step 1, run `curl -s http://localhost:8010/api/version` → `commit` is `"8df9812ed349"`, the first 12 characters of the sha passed in, not the full 40.
2. Rebuild without the variable: `BUILD_COMMIT= docker compose up -d --build backend`, then `curl -s http://localhost:8010/api/version` → `commit` is `"unknown"`.
3. Rebuild with a short value: `BUILD_COMMIT=abc1234 docker compose up -d --build backend`, then `curl -s http://localhost:8010/api/version` → `commit` is `"abc1234"`, unchanged.
4. Open `backend/app/routers/version.py` → it contains no commit string literal; the value comes from `get_build_commit()`.

### Criterion 3: the response body is a Pydantic schema in backend/app/schemas/
Prerequisites: the stack from Criterion 1.
1. Open `http://localhost:8010/docs` in a browser and expand `GET /api/version` → the 200 response schema is `VersionResponse` with fields `version` (string) and `commit` (string), both required.
2. Open `backend/app/schemas/version.py` → `VersionResponse` is a `BaseModel` declaring `version: str` and `commit: str`.

### Criterion 4: unit and integration tests cover the set and unset commit paths
Prerequisites: `uv` installed. No database is needed: with `DATABASE_URL` unset the app's startup skips the notes schema and the version endpoint still answers.
1. Run `uv run --directory backend pytest -q tests/unit/test_version_service_unit.py tests/unit/test_config_unit.py` → the run passes: its summary line reports no failed or errored test and the command exits 0.
2. Run `uv run --directory backend pytest -q tests/integration/test_version_integration.py` → the run passes: no failed or errored test on the summary line, exit code 0.
3. Run `uv run --directory backend pytest -q -k build_commit` → the selected tests include both set and unset cases (names containing `when_set` / `from_build_commit_env` and `when_build_commit_unset`), and the run passes with exit code 0.
