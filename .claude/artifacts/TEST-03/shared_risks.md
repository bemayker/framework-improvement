## Potential conflicts with other independent features

`feature_map.md` flags this explicitly in `shared_risk_notes` for both rows: **"⚠️ both TEST-02 and TEST-03 touch the FastAPI app entry (router registration); serialize if run concurrently."** TEST-02 (Health endpoint, a ClickUp tracker item) and TEST-03 both depend only on TEST-01, which is Done, so both are ready and neither depends on the other — they are independent and could be dispatched concurrently. Concrete overlap:

- `backend/app/main.py` may also be modified by **TEST-02** (independent, could run concurrently) — the flagged conflict. Both features add an `include_router(...)` line inside `create_app()`, and TEST-03 additionally adds a `lifespan`, CORS middleware, and an exception handler. Two concurrent edits to this one small factory will conflict textually.
- `backend/tests/unit/test_main_unit.py` may also be modified by **TEST-02** (independent) — `test_create_app_registers_no_feature_routes` asserts `custom_paths == set()` and breaks for *whichever* feature registers a router first; both features must rewrite the same test function.
- `backend/app/core/config.py` may also be modified by **TEST-02** (independent) — TEST-01's comments there anticipate TEST-02 wiring up the database, so TEST-02 may edit the same `Settings` dataclass that TEST-03 extends with `frontend_origin`.
- `backend/tests/conftest.py` may also be modified by **TEST-02** (independent) — the file's own docstring says TEST-02 "wires those fixtures in here", and TEST-03 adds exactly those DB fixtures plus a changed `client` fixture. High-probability semantic conflict, not just textual.
- `backend/pyproject.toml` and `backend/uv.lock` may also be modified by **TEST-02** (independent) — if TEST-02's health check touches the database it adds the same SQLAlchemy/psycopg dependencies. `uv.lock` conflicts are best resolved by re-running `uv lock` after the merge rather than hand-editing.
- `.env.example` may also be modified by **TEST-02** (independent, lower probability) — additive, single-line, easy to resolve.

**Dispatch advice (assisted mode):** serialize TEST-02 and TEST-03 rather than building them in parallel. Whichever merges second should rebase and re-run the backend suites before its PR goes green, paying particular attention to `main.py`, `conftest.py`, and `test_main_unit.py`. If both must run concurrently, land TEST-02 first (it is the smaller change to `main.py`) and let TEST-03 rebase onto it.

**No conflict expected on the frontend or E2E surface:** TEST-02 is backend-only, so `frontend/src/**`, `e2e/tests/TEST-03_*`, and the TEST-03 UAT artifacts are exclusive to this feature. TEST-01 is Done and merged, so its files are a stable base; TEST-03's edits to `LandingPage.tsx` keep TEST-01's test ids and heading text intact so `e2e/tests/TEST-01_static_landing_page.spec.ts` and `LandingPage.test.tsx` keep passing.
