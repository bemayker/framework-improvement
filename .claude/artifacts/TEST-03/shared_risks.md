## Potential conflicts with other independent features
TEST-01 is Done, so the only item that can run concurrently with TEST-03 is **TEST-02 (Health endpoint, `depends_on: [TEST-01]`, currently `todo`, tracker-resident)**. `feature_map.md` already flags the pair. Concrete overlaps:

- `backend/app/main.py` may also be modified by **TEST-02** (independent, could run concurrently) — both items register a router on the app factory. This is the flagged conflict; **serialize the two builds** rather than running them in parallel.
- `backend/app/core/config.py` may also be modified by **TEST-02** — TEST-01's comments assign DB connectivity to TEST-02, while TEST-03 must introduce it (plan assumption 1). If TEST-02 is planned or built independently, both would touch the same settings object.
- `backend/app/core/db.py` (**created here**) is the file TEST-02 was expected to create. Whichever item lands second must consume the existing module instead of recreating it; TEST-03 designs it to be reusable by a health check.
- `backend/tests/conftest.py` may also be modified by **TEST-02** — TEST-01 documented the DB fixtures as "wired in at TEST-02", and TEST-03 wires them in now.
- `backend/tests/unit/test_main_unit.py` may also be modified by **TEST-02** — its "no feature routes" assertion breaks for whichever router is registered first.
- `backend/pyproject.toml` / `backend/uv.lock` may also be modified by **TEST-02** if it adds its own dependencies; concurrent lockfile regeneration conflicts almost always.
- `.github/workflows/pr-tests.yml`: TEST-03 changes the service startup and integration-test environment. Any concurrent item touching CI would conflict; none is planned.

No conflict on the frontend: TEST-02 is backend-only, so `frontend/src/**` and `e2e/**` are TEST-03's alone.

**Recommendation (assisted mode — dispatch advice):** merge TEST-03 before starting TEST-02, or re-plan TEST-02 after this merge so it builds on `db.py`, `config.py`, and the conftest fixtures TEST-03 lands rather than duplicating them.
